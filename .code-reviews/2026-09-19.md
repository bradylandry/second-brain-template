## Medium

### Git `--author` filter never expands — `collect_git_activity` always returns empty
- **File**: `scripts/narrative_generator.py:67`
- **Issue**: `subprocess.run` is called with a list (not `shell=True`), so `--author=$(git config user.email)` is passed as the literal string `$(git config user.email)` to git. Git interprets this as a regex pattern looking for a committer whose email is literally `$(git config user.email)` — which matches nobody. The function returns `"(no git activity)"` regardless of actual commits. This makes the git activity input to the narrative LLM permanently empty, defeating the primary data source.
- **Fix**: Resolve the user's git email in a separate call before constructing the git log command:
  ```python
  email_result = subprocess.run(
      ["git", "config", "user.email"],
      capture_output=True, text=True, check=False, timeout=5,
  )
  user_email = email_result.stdout.strip()
  # then use: f"--author={user_email}"
  ```

## Low

### Unquoted heredoc expands user-provided variables — potential command injection for vault owners
- **File**: `vault/research-skill-graph/new-project.sh:63`
- **Issue**: The heredoc used to generate `index.md` and stub files uses `<<EOF` (not `<<'EOF'`), so shell variables and command substitutions in user-provided inputs (TITLE, QUESTION, SCOPE_IN, etc.) are expanded at write time. If a user accidentally enters backtick sequences like `` `rm -rf ~` `` at a prompt, the shell executes them. Severity is low because this is a local script run by the vault owner against their own machine, but it's still unexpected behavior.
- **Fix**: Quote the heredoc delimiter to prevent expansion: `<<'EOF'`. Use printf or a templating approach for the few places where legitimate variable expansion is needed (like `$TODAY`, `$TITLE`), or echo those in separately.
